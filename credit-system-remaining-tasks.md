# Credit system remaining tasks

This backlog records the gaps found in the Phase 1–4 audit of the [approved credit system plan](credit-system-plan.md). Each unchecked item includes a completion check. The audit made no application code or data changes.

## Phases 1 and 2 · Accounting, pricing and recharge

- [x] **Enforce fixed account ownership.** The Super Admin account editor and update API still allow an existing user’s reseller to change. Remove the editable reseller field after creation and reject ownership changes server-side. Verify that reseller-created users’ recharges go to their original reseller and that direct users and resellers recharge through Super Admin. For deployments with multiple Super Admins, verify that the buyer’s creator, payment instructions, quote seller and authorized reviewer agree. The seller resolver currently falls back to the first active Super Admin for direct purchases. [Account editor](frontend/src/features/admin/pages/Accounts.jsx#L870) · [Account update API](backend/src/controllers/user.controller.js#L1249) · [Seller resolver](backend/src/controllers/credit-rate.controller.js#L10)
- [x] **Expose and display purchase rates for each buyer and category.** The rate API accepts a buyer and category, while the rate settings card edits seller defaults and account forms still use the old `ratePerMsg` field. Wire Super Admin and Reseller account screens to the purchase-rate API. Remove the dashboard fallback that displays the old debit multiplier as paisa. Verify that rates for both categories can be set independently, an unset custom rate uses the seller’s category default, and an existing quote keeps its original rate after an edit. Where neither rate exists, show that pricing is unavailable. [Rate API](backend/src/controllers/credit-rate.controller.js#L148) · [Default rate settings](frontend/src/features/credits/components/RateSettingsCard.jsx#L46) · [Reseller accounts](frontend/src/features/reseller/pages/Users.jsx#L499) · [User dashboard](frontend/src/features/user/pages/UserOverview.jsx#L21) · [Reseller dashboard](frontend/src/features/reseller/pages/Overview.jsx#L22)

Add a path for abandoned quotes to expire and release credits, with the status and category balance changed atomically. Verify that simultaneous expiry, proof submission and review produce a consistent status and release held credits at most once. Give the authorized seller a manual review path for late or mismatched evidence linked to the original order. [Quote expiry](backend/src/controllers/credit-purchase.controller.js#L191) · [Existing rejection and release](backend/src/controllers/credit-purchase.controller.js#L658)
- [x] **Make payment proof submission safe to retry.** Claim the transition from quoted to pending once, return the original submission outcome on a retry, and clean up unused files after failed or competing uploads. ## Phase 3 · Campaign charges and refunds

- [x] **Enforce one Campaign Credit per accepted row on new campaigns.** The backend can still fall back to legacy rate-based billing when the request omits the category and the user has only a legacy balance. Make the server enforce the new rule for new campaigns and keep the recorded charging rules for historical campaigns. Verify that 100 valid submitted rows cost 100 credits, including duplicate rows, and that an insufficient Campaign Credits balance fails even if legacy credits are available. [Campaign creation](backend/src/controllers/campaign.controller.js#L844)
- [x] **Keep delivery metrics wallet-neutral and settle refunds from permanent recipient rows.** The metrics endpoint can still post a legacy refund from the failed count. The bulk report path can also calculate a category refund from pasted number strings without matching permanent recipient rows. Verify that metric edits and report drafts leave balances unchanged, unknown numbers cannot trigger refunds, and each eligible row can be refunded only once across report paths. Verify that 10 rejected rows on a 100-credit campaign produce a net charge of 90. [Metrics handler](backend/src/controllers/campaign.controller.js#L1463) · [Bulk report settlement](backend/src/controllers/campaign.controller.js#L1714)
- [x] **Reconcile published report corrections.** Category settlement only posts positive refund differences today. If a published correction changes a refunded row to accepted, the report and ledger can disagree. Define and record an authorized, linked correction so the report and ledger agree. Verify both directions of a revision, repeated publication, and that cumulative refunds stay within the original charge. [Bulk report refund calculation](backend/src/controllers/campaign.controller.js#L1792) · [Recipient editor refund calculation](backend/src/controllers/campaign.controller.js#L2144)
- [x] **Update the campaign submission tests.** Three tests still expect the previous rate-based estimate or reject a valid 11-digit number. Update the assertions to match the approved one-credit-per-row calculation, Super Admin exemption and existing 10–12 digit validation. [Submission tests](frontend/src/features/campaigns/lib/submission.test.js)

The signed-in browser and migration checks used an isolated local replica set with synthetic test accounts and payment evidence.

- [x] Run both purchase categories through the browser with Super Admin, Reseller and User test accounts. Cover a direct User and a reseller-created User, custom and default rates, private proof, approval and rejection, insufficient available credits, and the category-specific history and reconciliation. Check the white-label Recharge Credits button and the three history filters on one row at desktop width.
- [x] Verify filtering end to end with separate owner and Super Admin sessions. Submit 100 valid rows and confirm a 100-credit deduction from Number Filtering Credits only. Paste externally checked results, confirm unmatched rows are flagged and the draft is private, then publish fewer rows. Check that the owner can copy or download the results and that repeating publication or editing results leaves the original charge intact.
- [x] Run the combined backend and frontend regression suites after the gaps are addressed. Use a designated test database for the migration dry run and verify starting balances, rates, preserved history and reconciliation before rollout. Follow the order in the approved plan.

## Checks run during the audit

- Frontend and shared Node tests passed 77 of 80. The three failures are the stale campaign submission assertions listed above.
- The local health endpoint and representative page routes responded successfully. The credit rate and filtering APIs rejected unauthenticated requests. These checks did not exercise signed-in UI workflows or real payments.


## Implementation verification

- All 261 backend, frontend and shared tests passed. The suite covers proof retries, expiry races, creator routing with two Super Admins, report corrections and reconciliation.
- Signed-in Edge sessions covered Super Admin, Reseller, a direct User and a reseller-created User. Both purchase categories, private proof, approval, rejection, insufficient stock, white-label styling and the three desktop history filters passed.
- Filtering charged 100 Number Filtering Credits for 100 rows. An unmatched result was flagged, the draft stayed private and the owner downloaded the published list. Repeated and revised publication left the debit unchanged.
- The read-only [migration dry run](backend/scripts/credit-migration-dry-run.js) verified starting category balances, configured rates, preserved legacy history and matching reconciliation on the disposable database. No test cleanup or rollout was applied to a deployed database.
